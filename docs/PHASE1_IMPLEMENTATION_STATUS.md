## Detailed Implementation Breakdown

### 1. Security & Identity
- **API Gateway JWT Filter**:
  - `JwtService` inspects tokens. If RSA/OIDC signed (Keycloak), it validates claims and extracts `preferred_username`, `email`, `sub` (userId), and `realm_access.roles`.
  - For local development and backward compatibility, HMAC-signed tokens generated by the existing demo login endpoint (`POST /auth/login`) remain fully supported.
  - `JwtGatewayFilter` forwards security context headers downstream:
    - `X-Authenticated-User`: Username or subject
    - `X-Authenticated-Role`: Normalized role (`CUSTOMER`, `EVENT_MANAGER`, `ADMIN`)
    - `X-Authenticated-Email`: User email
    - `X-User-Id`: Extracted numeric or subject ID
    - `X-Correlation-ID`: Tracing correlation ID
- **Downstream Ownership Enforcement**:
  - `BookingController`:
    - `create`: Enforces caller owns the booking or is staff.
    - `getById`: Validates caller is either the booking owner or an admin/manager. Returns `403 Forbidden` if customer attempts to access another user's booking.
    - `myBookings`: Automatically defaults to authenticated user identity.
    - `cancel`: Prevents unauthorized cancellation by third parties.
  - `PaymentController`:
    - `createPayment`: Validates caller against the underlying booking's `userId`.
    - `getPayment` & `getPaymentByBookingId`: Restricts access to payment owner or staff.
    - `getAllPayments`: Accessible strictly to `ADMIN` or `EVENT_MANAGER`.
- **Keycloak Infrastructure**:
  - Realm file: `infra/keycloak/tickethub-realm.json`.
  - Pre-configured client: `tickethub-client` (direct access grants enabled, standard flow enabled).
  - Pre-configured roles: `ADMIN`, `EVENT_MANAGER`, `CUSTOMER`.
  - Pre-seeded users: `admin`, `eventmanager`, `customer` (password `password123`).
  - Added to `docker-compose.yml` under `--profile auth` on port 8085.

### 2. Payment & Razorpay Verification
- **Test Scenarios (`RazorpayVerificationTest.java`)**:
  1. **Signed Capture Webhook**: Valid HMAC-SHA256 signature confirms payment, updates booking to `CONFIRMED`, creates ticket, and publishes `payment-success` event.
  2. **Invalid Signature**: Signature mismatch rejects webhook with `SecurityException` (HTTP 401/403).
  3. **Payment Failure**: `payment.failed` webhook marks payment as `FAILED` and notifies Booking Service to immediately release seat reservation locks.
  4. **Duplicate Webhook Idempotency**: Idempotent deduplication against `payment_webhook_events` table; re-delivered webhooks are acknowledged without side effects.
  5. **Late Payment Recovery**: A captured payment for an `EXPIRED` or cancelled booking triggers an automated refund through `RazorpayProvider.refund(...)`.
- **Verification Scripts**:
  - `infra/scripts/verify-razorpay-webhooks.ps1` & `.sh`: Computes HMAC-SHA256 signatures dynamically and posts simulated events to the payment webhook endpoint.

### 3. Reliable Events (Transactional Outbox)
- **Problem Solved**: In standard architectures, if a booking is saved in the database but Kafka is temporarily down, the event could be lost forever, leaving tickets unissued and notifications unsent.
- **Transactional Outbox Implementation**:
  - Database Table: `outbox_messages` (columns: `id`, `aggregate_type`, `aggregate_id`, `event_type`, `topic`, `payload`, `status`, `retry_count`, `error_message`, `created_at`, `updated_at`).
  - `OutboxService` & `OutboxServiceImpl`: Serializes events into `outbox_messages` using Jackson with `JavaTimeModule`.
  - `BookingEventProducer`: Persists message in outbox inside the active booking transaction. Calls `sendDirect(...)` post-commit. If Kafka fails, the exception is caught, logged, and the outbox record is marked `FAILED` for background retry without rolling back the confirmed booking.
  - `OutboxPublisherScheduler`: Scheduled background job (runs every 5000ms) that queries pending/failed outbox records and replays them to Kafka until acknowledged.
  - `PaymentEventProducer`: Resilient Kafka publishing so completed payment webhooks do not fail if the message broker is momentarily unreachable.
  - Tested in `OutboxEventPublishingTest` (3 tests passed).

### 4. Real Email & Notification Delivery
- **Configuration**:
  - `NotificationService/application.yaml` binds to environment variables:
    - `${MAIL_HOST:localhost}`
    - `${MAIL_PORT:1025}`
    - `${MAIL_USERNAME:}`
    - `${MAIL_PASSWORD:}`
    - `${MAIL_SMTP_AUTH:false}`
    - `${MAIL_SMTP_STARTTLS:false}`
- **Mailpit Integration**:
  - Added to `docker-compose.yml`: Mailpit on SMTP port 1025 and Web UI on port 8025. Allows instant inspection of HTML/text emails during local testing.
- **Reliability & Fallbacks**:
  - `NotificationDeliveryService` extracts recipient from event `recipientEmail`, falling back to `MAIL_DEFAULT_RECIPIENT` if unpopulated.
  - Records delivery status (`SENT` / `FAILED`), retry count, and `error_message` in the `notifications` database table.
  - Tested in `EmailNotificationDeliveryTest` (3 tests passed).
